## Construcción y promoción propuesta

1. En CI confiable, obtener un commit aprobado exacto y árbol limpio, fijar versión de herramientas, plataforma, Dockerfile y contexto `apps/api`, materiales externos y argumentos. Construir sin tráfico y publicar en registro privado; registrar y verificar una atestación de procedencia firmada emitida por el builder, con commit, contexto, materiales y digest OCI. Etiquetas, nombres de imagen, variables y labels son metadatos declarados, no prueba suficiente. Consultar digest al registro y verificar firma, sujeto, commit y política del emisor antes de promover.
2. Elegir digest de manifiesto específico de plataforma. Si se usa un índice multiplataforma, registrar índice, plataforma, manifiesto hijo y digest de configuración OCI; el digest de manifiesto y el image ID Docker (config) son distintos. Mantener el manifiesto y capas en el registro y preservar la misma plataforma para migración y servicio.
3. Coolify soporta aplicaciones tipo Docker Image que consumen `registro/repositorio@sha256:<digest>` y no construyen desde Git ni usan autodespliegue de Git. Los recursos reales actuales son Dockerfile: convertirlos o crear sustitutos con transferencia de dominio, configuración, red, secretos, salud, límites y rollback exige un diseño de corte de tráfico, ensayado en un recurso aislado y en staging. No asumir que una modificación de build pack de la aplicación existente es segura ni que un recurso duplicado con el mismo dominio no causará conflictos. Verificar en Coolify 4.5.3 la imagen digest seleccionada y que no se reconstruye; reservar ruta y controlador de tráfico, aprobar transición y mantener reversión.
4. Guardar registro durable de commit completo, atestación, digest del manifiesto y config/plataforma, UUID del recurso y despliegue, fecha y resultado. Al desplegar, consultar el historial de Coolify y `docker inspect`: comparar el ID de configuración del contenedor con el config del manifiesto hijo verificado y la referencia/digest observada. La etiqueta `image:commit` o el ID Docker por sí solos no prueban la asociación con Git.

## Migración futura antes del tráfico

Tras probar la transición puente, bloquear concurrencia, validar UUID/URL/base, respaldo consistente y restauración aislada. Para cada ambiente, fijar `IMAGE` a la referencia de registro por digest de la nueva release y verificar procedencia, plataforma y config como arriba. Proveer configuración de la aplicación por archivo temporal exclusivo modo 0600, creado en un directorio protegido sin mostrar valores, eliminarlo al terminar; la URL debe ser la del destino verificado. Ejemplo conceptual para una operación futura autorizada:

```sh
docker run --rm --network coolify --platform linux/amd64 --env-file ARCHIVO_SECRETO --entrypoint /bin/sh REGISTRO/IMAGEN@sha256:DIGEST -c 'cd /app && /app/.venv/bin/alembic upgrade 013 && /app/.venv/bin/alembic current && /app/.venv/bin/alembic check'
```

El ejemplo no verifica destino, respaldo, concurrencia ni aprobación; no ejecutarlo solo. No exponer puertos ni aplicar etiquetas de proxy; `--network coolify` debe confirmarse en el momento. Asegurar que el archivo contiene todas las variables requeridas sin opciones extrañas y que el proceso no las registra. Usar el mismo manifiesto por digest y plataforma en la aplicación Coolify, registrar digest y resultado y no reintentar automáticamente si hay error. Verificar `013`, integridad, readiness de la API puente, disponibilidad y controles posteriores. Luego publicar el mismo digest y comparar el config del contenedor en ejecución. Si falla, detener el proceso y usar solo la recuperación aprobada; `downgrade` destruye datos financieros. Cualquier cambio de producción requiere aprobación explícita para destino, operación y plan de recuperación.
